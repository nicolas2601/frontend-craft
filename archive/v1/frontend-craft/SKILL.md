# Frontend Craft

**The user supplies the subject and goal. You supply the design judgment.** A short request must not require a second prompt listing fonts, components, assets and animations. Build the product, not a report about following a skill.

**Anti-slop is an acceptance constraint, not a style preset.** Reject interchangeable structure, invented proof, unfinished focal assets, decorative-only interactions and unsupported completion claims using the [observable rejection criteria](references/professional-review-loop.md#6-rejection-examples-not-a-new-template). Fix the observed cause; changing colors, names or adding effects is not a repair.

**Small, open-weight or Chinese-model host (DeepSeek, Kimi, Qwen, GLM, MiniMax), tight context, or a run that skipped steps?** Read [Operating card](references/operating-card.md) first and follow its 8-step loop literally; it gives the same method as short imperative steps with an artifact per step, tool discipline and a no-vision fallback. Capable models can start below.

Read [Product craft foundation](references/product-craft-foundation.md) first. This adaptation of the user-designated Noel Santiago playbook is the primary method: **understand → commit to a world → prove the visual system → build from it → inspect → correct → retain scoped feedback**. Optional skills support this method; they do not replace it.

The [complete source and staged reading map](references/noel-playbook-guide.md) are bundled too. Read the source sections relevant to the task; do not substitute this short core for its detailed system, component, motion and feedback methods. Prior demos are not the base or a default visual style.

**Apply through artifacts, not declarations.** For a new expressive site, use this order before writing a full page:
1. Inspect actual subject/composition reference views (Pinterest for mood and material, Awwwards/Lazyweb/design-screenshots for live structure and motion, Figma when the user supplies a file, the incumbent and 2-4 competitors); open them at size and keep source/rights notes per [inspiration research](references/inspiration-research.md). Reading design advice is not viewing a reference.
2. Check fitting component and media routes before committing to stack or drawing the focal object. Make bounded discovery calls through available CLI/MCP/helpers; keep the actual candidate or blocker, not an assumption that custom code is best.
3. Render two small, genuinely different first-view studies. Choose by the visitor's job, intended feeling and visible composition—not a paragraph describing each.
4. Prove one complete useful interaction at desktop and narrow widths, including visible feedback, accessible state and recovery, before repeated cosmetic revisions or secondary sections.
5. Expand the selected system, then inspect and correct the delivered states.

Use the [professional review loop](references/professional-review-loop.md). Read applicable procedures and Noel source sections at their stage, not the entire catalog at once. Keep **job → source → artifact/decision → observed check or blocker** in existing context; recover it after compaction. Missing access needs an honest fallback. Reading, hashes and self-scores prove neither application nor quality; see [reliability limits](references/model-portability.md#7-reading-is-not-application). This sequence does not turn a small scoped edit into a new design project.

**Delegate expressive or multi-part builds to specialist agents.** If the host has a subagent/task tool, the main session is the orchestrator and runs the ten `fc-*` specialists of the [agent roster](references/agent-roster.md) stage by stage: reference scout + UX architect + **two art directors on different organizing axes** in parallel for direction; system designer + component sourcer + asset artist in parallel for proof; the builder for one complete interaction, then delivery with the motion agent; the a11y auditor and finish-gate reviewer inspect independently at every gate. Only the orchestrator spawns agents; a reviewer never reviews its own output; a gate withholds promotion, it does not sandbox. Hand each agent the user brief verbatim, approved artifact paths with hashes, its writable lane and the required `STATUS/EVIDENCE` return. With no subagent tool, play the roles in sequence and keep the same artifacts. Skip delegation for a small scoped edit (zero to two agents), and never delegate the final judgment to a producer's "done".

## 1. Establish the real job

Read project instructions, current `PRODUCT.md`/`DESIGN.md`, dependencies, relevant components and working-tree status. Preserve user changes, required behavior and genuinely approved identity. Distinguish approved constraints from the agent's own proposals. A rejected generated design record is not a brand lock.

Classify each surface: **Persuade** (decide/act), **Experience** (explore), **Operate** (complete a task), **Read** (understand). Infer a small, explicit proposal for missing low-risk details; ask only one consequential blocking question. Do not expand a short brief into a business platform.

For an audit, report evidence without editing unless fixes are requested. Work only in the assigned project. Old fixtures, neighboring projects and examples do not turn a new request into their task or an evaluation exercise.

Check actual capabilities: references, editing, project checks, browser and screenshot interpretation. Distinguish installed, discoverable, permitted, quota-available and successfully used. A missing MCP name does not rule out a supported CLI/helper; an installed Hub CLI is not an image generator. If image understanding is unavailable, functional work can continue, but visual quality remains unverified. Never fabricate calls, screenshots, assets or measurements. In Nico's environment all browser interaction uses Playwright MCP. When the Figma MCP is connected, read an approved design with its context/screenshot tools; write into a Figma file only when the user asked for it.

## 2. Choose a direction, not a collection of effects

Find the visitor's question, the next useful action and the subject's actual artifacts, materials, constraints or outputs. Define a concise premise: **this product's specific thing becomes this composition or interaction, making the visitor feel this because of this visible/temporal choice**. Feeling needs a concrete mechanism—scale, pacing, material, typography, reveal or manipulation—not the adjectives premium/clean/editorial. State proposed fictional details as assumptions; never invent endorsements, credentials, research or business evidence.

Inspect the incumbent and 2–4 relevant references. Name **take this mechanism → becomes this feature here → leave this reference's identity**. Separate composition, interaction and material references; a famous company name or a skill title is not a reference inspection. Keep source/date and rights notes concise.

For an unpinned new direction, compare two small **visual** composition studies using the same realistic content and constraints: a sketch, prototype or rendered slice, not two paragraphs. Name the actual difference in organizing mechanism, hierarchy and useful interaction. A palette/type swap is not another concept. Choose against the brief and resources without asking the user to art-direct every detail. Carry one coherent direction forward, not two full apps or a blend of every reference.

Use [composition and personality](references/composition-and-personality.md) to compare the actual organizing mechanism, information order, focal scale and interaction—not two skins of the same section stack. Build the architecture from the visitor's questions instead of filling a fixed hero/cards/steps/FAQ/CTA template. A cream/monospace/oversized-heading diagram is not inherently more authored than a purple SaaS page. If a whole direction was rejected as basic or emotionless, reconsider its composition, medium and pacing; do not merely rename/recolor it or promote it to an approved reference. Keep useful conventions when they serve the task.

**Own the decision.** Anti-generic lists are diagnostic prompts, not laws banning a color, typeface, border, gradient or layout. Do not replace a fitting idea with another merely because a specialist calls its ingredients a common default. Conversely, a poetic thesis cannot justify pixels that miss the user's ambition.

Gather product material before consulting aesthetic advice. When UI Skills MCP is available, use a narrow `list_skills` search and retrieve one suitable director with `get_skill`; add at most two relevant specialists per stage. Record the actual ID and concrete decisions it informed. Without it, use verified local guidance or the bundled foundation and disclose the fallback. A retrieved guide does not include all its referenced tools or assets.

Respect manual-only metadata and the host's invocation rules. Reading a guide as reference data does not authorize running its commands, stripping invocation controls or installing its toolkit.

Precedence: **host safety/user scope → accessibility and product truth → verified approved project decisions → product-craft foundation → selected specialist advice → library defaults**.

## 3. Prove the main visual before expanding

For expressive, image-led work, the central artifact is part of the core task—not decoration to improvise after layout. Resolve it early using owned/licensed media, an actual product interface, a deliberate finished illustration or a task-relevant original 3D scene. Inspect it at presentation size and close-up.

Original composition does not require every asset to be newly drawn. Legitimate, truthfully attributed product media and well-chosen components can express the subject better than a weak reconstruction. Do not impose an unasked code-only/no-product-assets constraint and then call the resulting simplification creativity.

**An enlarged icon, rough contour, generic blob or placeholder diagram is not a finished hero asset.** SVG/CSS can be excellent final media, but their silhouette, proportions, detail, material language and composition must meet the chosen visual reference. “Drawn in code” does not prove craft, realism or authorship. Do not impose photorealism on an intentionally flat illustrated direction either. **Author SVG focal assets, icons, logos, diagrams and animated vector art through the [`svg-craft`](references/svg-craft.md) skill** (style packs with their own kits, seeded generators, a mandatory render-and-look loop, lint and a SVGO profile that keeps title/role/animation targets); freehand `d=""` paths are the fallback, not the default.

Inspect the focal artifact close-up before duplicating it. Wrong proportions, broken joins, illegible labels or disconnected parts are revision issues, not stylistic personality. After a focused repair, compare again with the intended finish. If it still misses, inspect a different feasible media/construction candidate before another cosmetic pass; do not accumulate SVG paths, blur or explanations to defend a failed visual. Do not consume the whole run polishing an unproven object while the main interaction remains untested. A generation/stock/controlled-scene route is valid only when its rights, scope and actual output fit.

If generation fails, do not silently lower fidelity or rename the fallback “editorial,” “atlas” or “minimal.” Try an appropriate already available/licensed resource or a feasible original asset strategy. Preserve the requested ambition; disclose any unresolved asset gap. A provider failure is not proof that another paid provider is necessary. No unapproved accounts, spending, uploads or generation.

Use [free-first asset production](references/free-assets.md) for actual provider/Space checks, public-only prompting, a verified anonymous HF ZeroGPU path and its bundled helper. Select a route that cannot use account credits when the requirement is free-only; “Hugging Face” or an open model license alone does not establish zero cost. Inspect the returned asset, not merely the API status.

Render the **first viewport and one useful signature interaction**, on desktop and a narrow layout, before filling out a long page. Compare actual pixels with the references: focal hierarchy, asset finish, scale, type, material, color proportions and task clarity. Fix the largest mismatch before expansion. A description of two concepts is not evidence that either looks good.

Read [creative media](references/creative-media.md) for 2D, 3D, explorable objects, scroll scenes or code-driven video. Choose the medium because it serves this concept, not to demonstrate every tool.

For short video assets, load the [internal HF video module](modules/hf-video/SKILL.md). It distinguishes generative inference from local composition, checks free-only/privacy conditions and reports real endpoint failures; do not claim an animated still is a generated scene or that an untested provider route works.

## 4. System before screens; useful components before spectacle

Use [design system](references/design-system.md) to establish one token source: semantic color roles, typography, spacing, shape, elevation, icons and motion. Match the product's voice and actual content. Palette quality includes proportions, lighting and materials—not tiny hex changes. Preserve a valued identity; reconsider a rejected proposal instead of recoloring it indefinitely.

For a new shared system, render a compact proof using the real components: hierarchy, surfaces, controls, relevant states, the signature piece and its narrow arrangement. Build the screens from those components. Fix cross-cutting defects once in the shared system. For a small task, the representative slice is the proof; no compulsory Storybook or documentation project.

A signature component must improve what someone can understand or do. Define **job → anatomy → input/state → visible consequence → recovery**. A four-item animated glossary is not automatically useful to someone choosing a service. Reuse project components, native behavior and installed accessible primitives before inventing a dependency or hand-writing a focus trap.

For a nontrivial reusable piece, use [component sourcing](references/component-sourcing.md): search the actual compatible registry, inspect finalists, adapt and render the fitting piece. In a compatible React project inspect the relevant HeroUI API; use the 21st CLI only to search and retrieve existing community components within the free retrieval allowance (never its generate/iterate/take features or the Magic MCP builder) for a warranted composite rather than merely naming it. Compare against project/native/headless behavior and respect free allowance/rights. Installed CLI documentation, a package declaration or an unused import is not integrated component use. Do not select a stack solely to avoid available fitting resources, bulk-install a template or force a framework.

Compare a bounded candidate set and record the actual query/source, choice or specific non-use reason, and adaptation; “custom is more original” is not enough to reimplement a solved behavior badly. Project dependency adoption can be a normal scoped build step when host/user policy permits it, unlike global installs, accounts or billing. If evidence is absent, do not claim the source was used. Keep promised visual consequences in view while the person decides.

Compose around realistic uneven content and reachable states: selected, pending, empty, error/retry, disabled, permission, long/missing data where relevant. Preserve input, prevent duplicate actions, distinguish missing from zero, and maintain focus/keyboard/touch access. Synchronize visible state and accessible descriptions; on mobile, keep the decision's essential visual consequence available instead of changing an offscreen preview. Do not invent fake loading, backend functionality or success to fill a checklist. Make demo-only behavior clear at the action.

## 5. Design motion with the experience

Use [interaction and verification](references/interaction-and-verification.md). For a cinematic or high-craft build, take one signature technique and two to four quiet supports from the [motion recipes](references/motion-recipes.md) instead of inventing code from scratch; Noel's frequency and reduced-motion rules still win. Give motion a job: feedback, continuity, explanation, direct manipulation or appropriate delight. Frequent tasks need fast response; rare scenes can carry more expression. Keep typography, material, geometry and movement telling the same story.

For a signature scene, specify **trigger → opening → meaningful intermediate change → resolved state → interruption/reverse → reduced-motion equivalent**. Show new information or a transformation; floating the same object and fading words is not a complete narrative.

For requested scroll-world, word/line reveals or Higgsfield-style camera effects, read the [concrete effect contracts](references/composition-and-personality.md#5-choose-an-effect-contract-not-a-cinematic-adjective) and applicable source guidance before implementation. Distinguish those effects instead of treating every request as parallax. Derive shots and progress states from the subject, keep cause and consequence legible, and check what the chosen medium actually controls. A generated clip's fps, a browser's rendering rate and smooth scroll are different; an approximate camera prompt is not exact camera/end-frame conditioning. The video module separates tested native limits from interpolation/upscale. Do not require a long user prompt, a fixed scene stack or paid Higgsfield generation.

When object exploration is requested, provide direct manipulation—not only an autoplay or arrow-button turn. Coordinate manual camera control with scroll-driven direction so they do not fight; keep reset, touch/keyboard alternatives and accessible information. Test the in-between states, not only a final pose.

Preserve normal scrolling, zoom and content selection. Budget blur, shadows, WebGL assets and offscreen work. Prefer economical properties/techniques, but do not claim GPU execution or a frame rate without measurement. Do not add particles, perpetual drift or a quota of animated elements as a quality badge.

## 6. Verify without certifying your own taste

Run the actual relevant tests/build/typecheck/lint. Then apply the [ship gate](references/ship-gate.md): its 13 auto-blockers, finding shape, fix order and `Ship: no / yes, with fixes / yes` verdict with a Coverage line. Inspect the real delivered surface, console, target widths, zoom/reflow, keyboard/focus, primary flow, recovery and reduced motion. Label synthetic data, emulation and untested hardware honestly. Screenshots saved are not screenshots inspected; readable DOM is not visual perception.

Compare the actual result with the brief and inspected references: **view/state → observed mismatch and visitor consequence → correction/replacement → re-render and remaining issue**. Include the first viewport, central media close-up, main interaction and narrow arrangement. Fix related high-impact problems in a focused batch, preserve known-good behavior and recheck the same states. Iteration can regress: retain the better candidate instead of blindly adding edits. Do not weaken checks or silently change conditions to hide a failure.

**Functional checks and visual acceptance are separate.** Three observations, unique labels, a coherent DESIGN.md or passing tests do not establish “visual authorship: passed.” Report what meets the intended direction, what falls short, and what remains for user review. If the user rejects the result, do not defend it by listing gates, skills or effects. A technically successful but visibly weak fallback remains unresolved.

Do not claim finished/premium while a known critical or major task, asset, interaction or visual mismatch remains. Stop to repair, replace the failed approach, or report the specific blocker. Independent rendered review, when available and authorized, is separate from the producer saying “done”; no aesthetic score or feature count certifies a price or perfection.

Deliver briefly: **what changed → what actually ran/was inspected → limits**. The workflow is internal; do not burden a normal creation request with a gate-by-gate essay. Keep significant project memory as **feedback → observed cause → exact correction → scope → approval status → regression check**. Do not generalize another client's preferences into universal rules.
