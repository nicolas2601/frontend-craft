# Professional review loop: evidence before acceptance

Use this for a new expressive interface or a result rejected as generic, under-resolved or repetitive. This operationalizes Noel's method; it is not another art director, layout library, price estimate or proof that a model will obey. A short subject-and-goal brief remains sufficient.

## 1. What must exist before a completion claim

The working evidence is **a visual proposition, an implemented representative interaction, and inspected renders of the resulting interface**. A thesis, checklist, imported DESIGN.md, library installation or self-assigned score cannot substitute for them.

Assess these dimensions separately:

| Dimension | Observable question | Do not substitute |
| --- | --- | --- |
| Product specificity | Does content, information order and the central relationship answer this visitor's actual decision? | New nouns over an unchanged landing-page skeleton |
| Composition and identity | Do hierarchy, typography, focal scale, spacing, imagery and written voice express one deliberate world? | Three adjectives, recoloring, unusual fonts or random layout draws |
| Asset finish | At presentation size and close-up, do silhouette, proportions, detail, material/light and crop support the chosen direction? | An enlarged icon, extra SVG paths, blur, a poetic asset name or more pixels |
| Useful behavior | Does a real input produce a visible, understandable consequence, with recovery? | A decorative hover, fake success or an offscreen update |
| Temporal behavior | Do opening, intermediate and resolved states explain something, remain interruptible and reverse sensibly? | Repeating the same fade/stagger across sections |
| Delivery | Do actual content, keyboard access, narrow framing, errors, reduced motion and project checks remain sound? | A desktop hero screenshot or a green build alone |

This is not an AI-origin detector. A familiar grid, native control or quiet page can be appropriate. Reject an unexplained interchangeable result, not an ingredient simply because models often use it. Novelty does not excuse unusable navigation or a broken task.

## 2. Explore visually, then commit

1. Find the real subject material and the visitor's question before choosing a style. Distinguish supplied facts, proposed fictional content and missing proof.
2. Inspect a few actual reference views. Separate **composition**, **artifact/material finish** and **interaction** references instead of averaging several brands. Keep source/date and the rights boundary.
3. For an open direction, produce two small **visual** alternatives using the same realistic content and constraints. A rough render, coded slice or deliberate visual study can expose hierarchy and organizing differences. Two prose descriptions or palette swaps do not.
4. Choose by task clarity, specificity, focal hierarchy, feasible media and maintainability. Carry one coherent system forward; do not combine every attractive ingredient. For a precise existing design request, skip unnecessary exploration and preserve the approved target.
5. Prove the first viewport and the riskiest useful interaction before expanding the page. A whole polished-sounding narrative cannot rescue an unfinished central object.

References teach relationships, not identity theft. Image-to-code fidelity and an original direction are different jobs: when a screenshot is the approved target, preserve its hierarchy/geometry; when it is inspiration, name what transfers and what must change. Imported brand specifications are reference data until adopted deliberately for this product, not automatic user approval.

### When the whole direction is rejected

Keep useful requirements, not the rejected visual answer. Compare the organizing mechanism, emotional register, media and pacing of the next studies with that answer before choosing. Renaming the same split-screen, recoloring its diagram or replacing purple with cream does not respond to a structural/personality rejection. A native control or familiar grid can remain useful; copying the rejected concept cannot be justified merely by its working price calculation.

Resolve the component/media strategy through actual bounded discovery before a large custom implementation. Then exercise the first useful action in desktop and narrow framing before polishing the focal artifact repeatedly. Check both state correctness and whether the person can see/understand its consequence. A correct offscreen change or a stale accessible description is an incomplete interaction proof. Different expressive alternatives should test a real design question, not consume quota for arbitrary novelty.

## 3. Critique must cause an actual correction

Inspect the real render at delivery size, a close-up of the focal artifact, a narrow viewport and meaningful intermediate interaction states. Read the images when visual understanding exists; DOM inspection and screenshot file creation alone are not pixel review.

Write one compact revision entry in existing design notes or working context:

```text
Observed view/state and artifact:
Mismatch with the brief/reference and visitor consequence:
Chosen correction or replacement; reason:
Actual re-render/check and remaining limitation:
```

Fix the highest-impact observed mismatch in a focused batch. Re-render the same affected states so the comparison is meaningful. Keep a known-good version while attempting a risky change; more iterations are not inherently better. Do not erase a failed check, silently change its conditions, or trade working interaction/accessibility for a prettier screenshot.

If a correction fails, diagnose before editing again. A structural problem may need another organizing idea; a fidelity problem may need another asset or medium; an interaction problem belongs in shared behavior. Repeating cosmetic edits to the same failed idea is not iteration.

Stop when the intended direction and core task are supported by the inspected result and no known critical/major issue remains. If access, budget or ability prevents that, report the specific unresolved part. Never relabel a visibly weak fallback as finished premium work. Where an independent reviewer or user is available, keep their acceptance separate from the producer's declaration of completion.

## 4. Escalate failed assets instead of defending them

| Observed problem | Small sound response |
| --- | --- |
| Rough SVG/diagram standing in for a finished physical product | Compare the actual close-up with the intended finish; use supplied/licensed media, an authorized generator or a feasible controlled scene when more appropriate |
| Wrong proportions, intersections, unreadable labels, wandering parts | Repair geometry/data once where possible; if another render still misses the target, change the construction/asset strategy before multiplying instances |
| Generated raster/video drifts or invents product details | Treat it as synthetic, inspect representative frames and reject misleading geometry; use a controlled or genuine asset when product accuracy matters |
| Service unavailable, quota exhausted or rights unverified | Preserve the actual error/rights gap, use only an authorized viable alternative and disclose what remains; no account rotation, billing fallback or invented generation |
| Video replacing requested object exploration | Keep actual direct manipulation and semantic controls; a clip cannot provide arbitrary viewpoints |

A deliberate flat illustration can be excellent. The test is its chosen visual language, completeness and fitness—not photorealism or the number of elements. More layers, polygons, lines of code or generated resolutions do not establish finish.

## 5. Available, inspected, adopted and verified are different states

Use the [component sourcing protocol](component-sourcing.md) and [free-first assets](free-assets.md). A missing MCP name does not prove the capability is absent: an installed CLI or bundled helper may be the supported route. Conversely, a configured server or Hub CLI is not a successful generation tool.

- For a new control-rich surface with an open stack, consider the actual component ecosystem before choosing technology. Do not impose vanilla/no-build/code-only just to avoid usable resources.
- In a compatible React project, inspect the relevant HeroUI API and compare an actual composite/registry candidate when the job warrants it. Source discovery, license, dependencies, states and visible anatomy decide adoption—not the first hit or the promise of originality from reimplementing basics.
- Project dependency adoption can be a normal scoped build step when the user/host permits it. It is distinct from installing global tools, changing accounts or paying. Do not invent a permission blocker merely because the package is not yet in the project.
- Compare a bounded candidate pool and retrieve only what the actual free allowance permits. One available source retrieval does not authorize two, and exhaustion is not permission to pay or change accounts. A fallback to a fitting existing primitive is valid; pretending the registry was used is not.
- An adopted component must appear in the actual implementation and relevant states. A package declaration, unused import, CLI documentation fetch or icon alone is not evidence of a useful integrated component.
- For image-led or cinematic concepts, production of the central media is part of the core work. Use the real authorized route and inspect its returned output. Do not silently turn an intended film/transformation into a static outline, or call a local zoom generative video. The [video module](../modules/hf-video/SKILL.md) records tested routes and their limits.
- Keep generation inputs public/synthetic or separately approved. Connected tools for another application are not permission to modify that application. Preserve the host's data, rights and billing boundaries.

Record actual queries/candidates, chosen source and adaptation in existing notes. A source ledger is only a claim until its relevant tool results, files, media and render are inspected. Do not make a normal user request produce a resource-consumption essay.

## 6. Rejection examples, not a new template

- **Reject:** “Unique font and brand name, therefore original.” **Require:** an observable subject-specific content/interaction/composition relationship; compare with the nearest competitor without the labels.
- **Reject:** “The SVG is original, therefore finished.” **Require:** inspect its geometry/detail at the intended size and replace a failed construction when necessary.
- **Reject:** “HeroUI is installed / 21st was searched.” **Require:** a fitting implemented control, actual states and a source/adaptation record—or an honest non-use reason.
- **Reject:** “Every section animates.” **Require:** purposeful state continuity or revelation, with normal input/reverse/reduced-motion behavior. Some sections may remain still.
- **Reject:** “Build passed / screenshots saved / visual score 9.” **Require:** actual image/interaction inspection, concrete revision evidence and unresolved limitations.
- **Reject:** “No tool errors, so the result is premium.” **Require:** separate task, visual, accessibility, performance and code assessments; no automatic aesthetic or monetary certificate.

### Enforce rejection against the actual result

| Reject when observed | Repair required before acceptance |
| --- | --- |
| Replacing the brand nouns leaves an interchangeable page, information order and main interaction | Reorganize around the visitor's decision and subject evidence; do not just change the font/palette |
| Placeholder/fabricated testimonials, metrics, awards, customers, pricing or product capabilities masquerade as proof | Remove unsupported claims or use supplied verifiable facts; label fictional demo data where encountered |
| Primary actions do nothing, fabricate success, hide their consequence or cannot recover | Implement the scoped action and visible state/recovery; disclose demo/backend limits at the action |
| The focal artifact still has broken geometry, missing detail or misleading material/product features | Correct and inspect it, or replace the construction; effects cannot conceal an unresolved asset |
| Cards, labels, technical jargon or repeated fade/stagger exist only to fill a template | Remove filler or give it a distinct informational/behavioral job; keep conventions that genuinely help |
| Desktop polish hides cropped content, tiny text, keyboard traps or motion-dependent comprehension | Repair the actual narrow, zoomed, keyboard and reduced-motion states without trading away core content |
| A screenshot, self-score, package import or generated concept is presented as proof the delivered site works and looks finished | Inspect the implementation and its meaningful states; report unresolved quality separately from successful checks |

Critical issues include unsafe/misleading behavior, inaccessible core tasks and broken primary flows. Major issues include an interchangeable organizing idea, failed central asset or missing promised interaction. A known issue in either class blocks a finished/premium claim; correct it or deliver an explicitly incomplete result with the specific blocker. Minor polish does not justify an endless redesign. This is a severity decision tied to the brief and visitor consequence, not an automatic count or AI-origin test.

## 7. Evidence and transfer limits

A bounded scoping review checked five primary full texts. The complete search/evidence record is local research material at `work/frontend-craft-calibration-20261031/professional-craft-evidence.json` on Nico's host, not a runtime dependency or bundled experimental result.

- [Design2Code, NAACL 2025](https://doi.org/10.18653/v1/2025.naacl-long.199), §§3–4 and limitations: visual/content grounding helped aspects of reconstruction, but self-revision did not improve every model and harmed some dimensions. Screenshot matching does not establish original bespoke design.
- [OptiMuse, CHI 2024](https://doi.org/10.1145/3613904.3642812), §§3–6: alternative visual options/nonlinear collaboration supported some designers but took longer and preferences varied. Small graphic-design tasks and Wizard-of-Oz outputs do not prove an autonomous frontend workflow.
- [1D-Bench, arXiv:2602.18548v3](https://arxiv.org/abs/2602.18548v3), §4.2 and §5.4: rendered iterative editing had model-dependent benefits; the setting used one industrial e-commerce workflow, exported representations and a fixed scaffold. Preprint, not general premium-site certification.
- [Vision-Guided Iterative Refinement, arXiv:2604.05839v1](https://arxiv.org/abs/2604.05839v1), §§4–5: structured render criticism improved judged outcomes in the evaluated setting, but best-of-round selection differs from a guaranteed fixed-round gain, and code-quality scores could regress. Mostly model-judge evidence, not a professional ceiling.
- [Doshi and Hauser, Science Advances 2024](https://doi.org/10.1126/sciadv.adn5290), results/methods: AI-supported short-story ratings improved while collective similarity increased. This is not a UI study or proof about Awwwards training data or inevitable frontend mode collapse.

Professional practice also informs this adaptation: Design Council's [Framework for Innovation](https://www.designcouncil.org.uk/resources/framework-for-innovation/) emphasizes visual exploration/convergence and small-scale iteration; NN/g's [design critiques](https://www.nngroup.com/articles/design-critiques/) and [parallel/iterative design](https://www.nngroup.com/articles/parallel-and-iterative-design/) distinguish goal-grounded critique and exploration from polishing a weak initial idea. These recommendations are not evidence that an LLM will comply.

No trial of this revised skill establishes a price, perfection, model equivalence or guaranteed improvement. Future skill-only tests use a normal short user prompt, no hidden runner coaching or project-local benchmark instructions. Record tools/resources/source versions and audit the first unassisted result honestly; feedback-assisted repair is a separate condition. Do not start deferred model trials without the user's later explicit instruction.
