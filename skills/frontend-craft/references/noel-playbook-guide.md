## Progressive source reading

Read the relevant source sections in addition to the core workflow, not the entire skill catalog:

| Work | Source sections to consult | Concrete output |
| --- | --- | --- |
| New direction or visual critique | 0–3; relevant case/feedback in 14–15 | Product/mode, direction, scope and actual reasons; no inherited category template |
| New or extended system | 4–5 | Shared semantic roles, hierarchy, material and component proof using real code |
| A component or product flow | 6–7 and 9 | Correct semantics/anatomy, useful reachable states, geometry, motion and recovery |

| Skill/tool or handoff selection | 16–17 and 20 | Only the relevant available specialist/tool, supported output and honest fallback |
| Repeated feedback | 3.3, 3.6 and 15 | Scoped correction and regression memory; preserve approvals without generalizing another client's taste |

Use section headings/search and complete bounded reads. Do not claim a section was read if the tool clipped its middle or end. Choose examples for their mechanism, never as the next project's palette, grid, mascot or subject. A prior demo is not the base; the source method and current brief are.

## Authority and availability

Nico designated this source as the primary design method. Host safety, explicit user scope, accessibility and product truth still win. Preserve the source verbatim for provenance; apply the technical/authorization adaptations in the foundation. Its historical cases, measurements and claimed private-suite tests are source testimony, not independently reproduced checks here.

No private `frontend-craft-suite` archive was found in the bounded Downloads scout: only the playbook was present. Its `/fe-*` commands, 23 skills, model-switch markers and browser/install scripts are therefore **described, not supplied or installed**. Do not fabricate their invocation or automatically run setup. The current host's real tools and browser policy remain authoritative.

The original source contains context-specific style preferences and broad technical shorthand. Do not turn a named client's approved preference into a universal palette/effect ban, infer guaranteed contrast from a focus recipe, or equate transform/opacity with measured GPU/frame-rate performance. Preserve required feedback across input methods and measure the actual implementation.

Likewise, the source's preference for SVG/CSS where suitable is not a requirement to make every protagonist a code drawing. Choose the medium and finish for the current product: a rich illustration, licensed/supplied photograph, generated raster or real interactive object may be appropriate. Follow [free-first asset production](free-assets.md) and [component sourcing](component-sourcing.md) rather than lowering fidelity or rebuilding a complex UI primitive unnecessarily.
