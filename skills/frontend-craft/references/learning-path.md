# Train the judgment, not an adjective

Use this for a learning request. Default to a direct explanation plus one concrete exercise; use Socratic questioning only when the user requests that teaching style. Do not impose a semester-long course before solving an immediate task.

## 1. The working loop

`observe → name the mechanism → reconstruct a small slice → compare → fix → transfer`

**Observe:** inspect a real render at its actual viewport, including a meaningful state change. Look first at the hierarchy and task, not the CSS.

**Name:** replace “looks premium” with a falsifiable description: one dominant region, a restrained accent role, stable loading dimensions, aligned numerals, an overlay related to its trigger.

**Reconstruct:** rebuild one mechanism in a tiny isolated surface using a different domain/brand. Preserve accessibility and content truth. Do not copy third-party assets or institutional branding.

**Compare:** inspect both at equal viewport/content conditions. Check type metrics, effective sizes, baseline alignment, density, radius nesting, feedback and keyboard behavior.

**Fix:** change the largest mismatch first; do not tune tiny shadows while hierarchy or data states are wrong. Recheck the relevant interaction, not just the image.

**Transfer:** explain when the technique is useful and when not to use it. A technique learned only in green Escala is not yet generalizable.

Keep a small decision notebook if useful: claim, evidence, decision, tradeoff. Review the result with fresh eyes; user testing is still needed for claims about actual users.

## 2. Six reconstruction exercises

### A. Hierarchy before effects

Take one representative operational screen. List its primary task, dominant region, secondary groups and next action. Rebuild the information layout in grayscale with realistic text before adding brand or animation.

**Evidence:** primary action remains identifiable; reading order is logical; long content does not destroy grouping. Explain what changed, not a subjective 10/10 score.

### B. One type family, multiple roles

Use an approved font and define body, metadata, heading, label and numeric roles. Match hierarchy with size, weight, leading and spacing—not five different font families. Test long Spanish names, accents, dates and tabular amounts.

**Evidence:** loaded font/fallback inspected; body and metadata remain readable at narrow widths and zoom; intended roles are consistent across two components.

### C. A seed is not an accessible palette

Choose a new brand seed. Derive semantic action/text/surface/focus roles. Measure the relevant foreground/background pairs. Include success, warning and error with text, not color alone.

**Evidence:** explain why a brand color might remain a surface while a darker shade becomes text. Verify normal/hover/focus/error states; do not reuse Escala's numbers as universal defaults.

### D. One component, complete behavior

Build a useful form or detail panel using the project's primitives. Include loading, validation, success, error/retry and long content. Preserve edits after a simulated recoverable failure.

**Evidence:** behavior test; keyboard path; no duplicate submit; clear pending/error message; a screenshot of a non-happy-path state.

### E. One purposeful motion

Choose a transition that actually explains continuity or feedback. Implement immediate activation feedback, a coherent origin/path, interruption and a reduced-motion alternative. Start with platform/CSS support; do not install a library just for a fade.

**Evidence:** exercise rapid reversal and keyboard dismissal. Explain what an animation adds, what it costs and how you checked it. Static screenshots alone do not prove fluidity.

### F. Transfer to a different product

Apply the same reasoning to an unrelated brand: a repair scheduler, library catalog or municipal form. Keep the workflow, change the expression. For a marketing storytelling surface, evaluate scroll-world separately from a daily operational app.

**Evidence:** the new product is distinguishable without its logo; native/accessible interactions remain familiar; content and semantic roles are honest; task completion does not depend on watching effects.

## 4. Prompts for an agent

### Learn an incumbent

> Use frontend-craft in learning mode. Read the design record, representative components/tests and relevant history. Inspect the current render if authorized tooling is available. Separate direct evidence, documented decisions and inference. Explain five transferable mechanisms with file/line or commit evidence, one tradeoff each, and one exercise. Do not invent the author's prompts or redesign the app.

### Build with a constrained model

> Use frontend-craft. First check your actual read/edit/shell/browser/image capabilities. Preserve the existing design system and framework. Complete one representative task flow with realistic states. Load only one visual director and up to two specialists for the current stage. If a skill is absent, use the verified discovery/installation instructions or the bundled fallback; never claim a missing tool ran. Run the appropriate checks, inspect the render if possible and disclose what remains unverified.

### Improve without replacing the identity

> Refine only the named surface. Keep factual copy, brand tokens, navigation and business behavior. Prioritize task hierarchy and the concrete visual/interaction defects in the render. Show Before/After/Why for changed decisions. Do not introduce a new animation framework, font family or generic template without a demonstrated need.

### Brand a new surface

> Establish audience, promise and surface mode from the brief. Select a small compatible reference set and explain transfer versus imitation. Commit to one visual grammar, define semantic roles and build one representative slice before scaling. Do not copy logos/assets or invent endorsement, user research or business results. Verify content, accessibility and rendered behavior.

### Evaluate a candidate model fairly

> Use identical briefs, repository revisions, tool budgets, assets and target viewports. Keep test outputs and screenshots for each candidate. Assess instruction following, functional correctness, accessibility, identity coherence and observed iteration cost separately. Do not treat a benchmark/model-card claim as frontend evidence. Mark unavailable visual inspection or human usability testing as a limitation.

## 5. What to measure

- **Process:** did the agent inspect the incumbent, explain references, preserve scope and run tools honestly?
- **Function:** can the primary task and recovery flow complete with the provided data/backend?
- **Accessibility:** what specific keyboard/focus/contrast/reflow checks passed, and what remains unchecked?
- **Visual craft:** is hierarchy, typography, spacing, palette and component behavior coherent with the brief? Include human judgment and concrete observations.
- **Performance:** what interaction/runtime measurement was actually taken? Record the device/build/context.
- **Efficiency:** how much time/iteration was needed to reach acceptable output under comparable conditions?

Do not compress these into a fabricated universal quality percentage. Strong code generation, attractive screenshots and actual product usability are related but different outcomes.
